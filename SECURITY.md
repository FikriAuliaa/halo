# SECURITY.md

> Rewritten for Phase 14 (B118) against the actual Supabase/Postgres implementation. The previous version described the pre-migration Firebase/Firestore architecture (`refactor: migrate backend from Firebase/Firestore to Supabase/Postgres`) and had drifted substantially from what's actually built; every section below was re-verified live against the running system rather than carried forward from the old text.

## Admin authentication and RBAC

Supabase Auth (email/password), admin-only — students never authenticate (`AGENTS.md`, ADR-002). Two roles, `ADMIN_KAMPUS` and `ADMIN_TELKOMSEL`, held in the `admin_users` table and looked up **live** on every request (never cached in the session JWT) — an improvement over the old Firebase custom-claims model, which required a token re-issue for a role change to take effect. Every admin Route Handler verifies the session and role independently of the client-side route guard (`middleware.ts`), which exists only for redirect UX and is documented as safe to disable entirely without opening any endpoint.

Sign-in and silent session refresh (`signInWithPassword`, `refreshSession`) run on a dedicated, throwaway Supabase client (`createScopedAuthClient`), never on the shared service-role singleton — see `src/lib/supabase-admin.ts`'s doc comment for the real, live bug this fixed (Phase 10-11 gate): calling either on the shared client mutated its session, so every later Storage call in the process silently authenticated as that admin instead of the service role.

## Row Level Security philosophy

Deny-by-default, and it stays that way: every table has RLS **enabled with zero policies** (`AGENTS.md`, `supabase/migrations/20260101000000_init.sql`). Because the client never talks to Postgres or Storage directly — every read and write goes through a Route Handler using the service-role connection, which bypasses RLS entirely — these zero policies are the backstop for a leaked anon key, not the primary access control. Verified live with the actual local anon key against every table and both Storage buckets (Phase 14 audit, below): every table returns `401 permission denied`; the private `proofs` bucket returns an empty list and `404 Object not found` for a file that demonstrably exists; the public `payment-assets` bucket allows anonymous **reads** (by design — the QRIS image is meant to be public) but refuses anonymous **writes** with `403`.

## Input validation

Every field is Zod-validated at the Route Handler boundary (server-authoritative) and additionally validated client-side for UX (`src/schemas`, shared definitions). Client-side validation is never trusted; it exists to avoid round-trips, not to enforce anything.

## Upload security

Implemented by `uploadProof` (student payment proofs) and `adminUpdatePaymentConfig` (admin QRIS replacement), sharing one pipeline (`src/server/storage/reencode-image.ts`, extracted in Phase 13): magic-byte sniffing (not extension) determines file type; declared MIME type, sniffed bytes, and file extension must all agree; size is checked before the file is fully buffered where the runtime allows; the accepted image is then decoded and **re-encoded** via `sharp` before it ever reaches Storage. Re-encoding, not sniffing alone, is the real control — a polyglot file can be simultaneously a valid JPEG and a valid script; decoding it as an image and re-emitting fresh pixel bytes discards anything that isn't actual image data, and strips EXIF metadata (which routinely carries GPS coordinates) as a side benefit for student privacy.

## Tracking token model

`order_ref` (public, low-entropy-but-fine identifier) and a CSPRNG tracking token (high-entropy secret) are minted together at reservation time (ADR-005). Only `sha256(token)` is ever persisted — the plaintext exists solely in the response body shown to the student once, never in application logs (verified live: a real order submission's tracking token does not appear anywhere in server output), never recoverable server-side. `POST /api/track` rate-limits both per-IP and per-`order_ref`, fail-closed.

## Secret management

No secret value is committed — `.env*` is gitignored except `.env.example`, which documents every variable's name and purpose with no real value (verified: `git grep` for common secret patterns and for the local dev service-role key/DB password against the tracked repo and the built `.next` bundle both return clean). Local development uses the Supabase CLI's local stack with fixed, non-sensitive demo credentials. `src/lib/env.ts` validates every server-side variable at module load — a _provided-but-malformed_ value fails fast with a named field; a missing one does not throw, since every field is optional and callers already handle the placeholder-config case. As of this audit, this module is actually imported (from `src/server/db/client.ts` and `src/lib/supabase-admin.ts`) — it previously was not, despite its own doc comment claiming otherwise, a real gap found and fixed during this pass. There are currently no genuinely-in-use `NEXT_PUBLIC_*` variables (the architecture has no client-side Supabase code at all); the previously-declared-but-unused `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_ANON_KEY` scaffolding was removed in the same pass rather than left as dead, misleading surface.

## XSS and CSRF posture

React's default escaping covers XSS for all rendered student/admin data; no `dangerouslySetInnerHTML` is used anywhere in the codebase. A nonce-based Content-Security-Policy (`src/middleware.ts`, Phase 14/B116) forbids `unsafe-inline` scripts and unlisted script origins; verified live that Next.js applies the per-request nonce to every script tag it injects and that every page (student and admin) still renders and functions with the policy enforcing, not report-only. CSRF: all mutating Route Handlers are same-origin `fetch` calls from the app's own pages, the admin session cookie is `SameSite=Strict`, and state-changing `GET` requests are never used.

## Security headers

Set on every response by `middleware.ts`: `Content-Security-Policy` (nonce-based, `strict-dynamic`, `frame-ancestors 'none'`, `object-src 'none'`), `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Permissions-Policy` denying camera/microphone/geolocation, and `Referrer-Policy` — `no-referrer` specifically on `/lacak` (the tracking page, which may carry a token in a query string a `Referer` header would otherwise leak to any linked resource), `strict-origin-when-cross-origin` elsewhere. `img-src` includes the actual configured Supabase Storage origin, resolved from `SUPABASE_URL` at request time rather than hardcoded, so it can't silently drift out of date or stay too permissive across environments.

## Rate limiting and abuse protection

Postgres-backed counters (`rate_limits` table) keyed by session, IP hash, or both depending on the endpoint's abuse shape (B115):

| Endpoint                          | Key                                           | Limit        | Reasoning                                                                                                                                                                                                                                                                                                                                                      |
| --------------------------------- | --------------------------------------------- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/numbers`                | IP hash                                       | 60/min       | Read-only listing; per-IP is fine even behind shared campus NAT                                                                                                                                                                                                                                                                                                |
| `POST /api/numbers/{id}/reserve`  | session                                       | 10/min       | Primary fairness control — a session-scoped budget doesn't punish a whole faculty behind one address                                                                                                                                                                                                                                                           |
| `POST /api/numbers/{id}/reserve`  | IP hash                                       | 100/min      | **Added in Phase 14.** A session ID is a client-supplied cookie value with nothing stopping a script from minting a fresh one per request to reset the per-session budget every time; this backstop bounds one address's total reservation churn regardless of how many sessions it cycles through, sized loose enough to never bother real shared-NAT traffic |
| `POST /api/orders`                | session                                       | 5/min        | Submission, not browsing — tighter budget is appropriate                                                                                                                                                                                                                                                                                                       |
| `POST /api/track`                 | IP hash **and** `order_ref`, both fail-closed | 20/min each  | Brute-force surface (guessing a token); a caller rotating IPs still can't brute-force one specific ref, and rotating refs still can't brute-force from one IP                                                                                                                                                                                                  |
| `POST /api/admin/session` (login) | IP hash **and** email, both fail-closed       | 10/5min each | Brute-force surface                                                                                                                                                                                                                                                                                                                                            |

Reservation hoarding beyond the churn concern above is structurally bounded by the reservation lifecycle itself, not just the rate limit: a session may hold at most one live reservation at a time (`reserveNumber`'s own guard), so no amount of rate-limit headroom lets one session tie up more than one number simultaneously.

## App Check — not applicable

The original spec called for Firebase App Check (reCAPTCHA Enterprise) on public endpoints. This is a Firebase-ecosystem product with no direct Supabase equivalent, and does not apply after the migration to Supabase/Postgres (per the explicit direction to not use Firebase). The rate limiting above and the server-mediated architecture (no client ever holds a credential capable of reaching the database or Storage directly) are the actual controls against scripted abuse; a bot-attestation layer was never load-bearing in this design and its absence is not a gap relative to what the rest of this document claims.

## Audit fields

`orders.verified_by` (admin UID), `verified_at`, `numbers.sold_channel`, and every admin mutation logged to the `audit_log` table with the acting admin's UID and role, a before/after snapshot, and (where applicable) a written reason — written inside the same transaction as the mutation it describes, never after the fact (verified live across Phases 10-13: every verify/reject, number inventory action, and configuration change produced a matching row). Audit logs never include the payment proof image itself, its raw bytes, or a minted signed URL.

## Least privilege

Two roles: `ADMIN_KAMPUS` and `ADMIN_TELKOMSEL`. Most operations are open to either (`ADMIN_PERMISSIONS` matrix, `src/domain/permissions.ts` — the single module imported by both server enforcement and client UI hiding). `ADMIN_TELKOMSEL` additionally holds the destructive/financially-sensitive powers: mark-sold-offline, force-release, order status override, package price changes and price confirmation, payment configuration, admin account management, and system config. Verified live (Phases 6, 12, 13) that `ADMIN_KAMPUS` is refused with `403` for every one of these, not merely hidden from its UI.

## PII inventory and minimisation

| Data                | Where                  | Sensitivity                                          | Minimisation                                                                                                                      |
| ------------------- | ---------------------- | ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Full name           | `orders.full_name`     | Moderate                                             | Retained for order lifetime; not collected beyond what's needed                                                                   |
| WhatsApp number     | `orders.whatsapp`      | Moderate                                             | Stored normalised, never displayed except to the order's owner (via tracking) and admins                                          |
| Email               | `orders.email`         | Moderate                                             | Same as above                                                                                                                     |
| University          | `orders.university`    | Low                                                  | —                                                                                                                                 |
| Payment proof image | Storage `proofs/`      | High (may reveal bank details, transaction metadata) | Private bucket, signed-URL-only access (5-minute TTL, minted per admin view and audited), EXIF stripped on ingest via re-encoding |
| Tracking token      | Hash only, in `orders` | High if plaintext (it's a bearer secret)             | Plaintext never stored, only shown once in the response body                                                                      |

Retention (OQ-8): 90 days after an order reaches a terminal state, order record retained. Not yet automated as a scheduled job — tracked as a known limitation (see the Phase 17 remediation report once written).

## Log redaction

Centralized, not per-call-site (`src/server/framework/logger.ts`'s `redact`, keyed by field name so a new event type can't forget to redact an already-known-sensitive field): `full_name`, `whatsapp`, `email`, `tracking_token`, `admin_note`, and `payment_proof_path` are replaced with `[REDACTED]` wherever they appear in a logged payload, at any nesting depth. Verified live in this pass, not only by unit test: submitted a real order with a distinctive name/email/phone number and grepped the actual server log output — zero occurrences of any of the three values, and zero occurrences of the tracking token from a separate real reservation.

## Secure error messaging

Student-facing errors use the centrally-enumerated `AppError` codes and safe messages (`src/lib/errors.ts`) — never a raw Postgres or Storage exception message, which can reveal table/column names or internal structure. `toHttpResponse` is the one place an unhandled exception is caught and converted to a generic `INTERNAL` error for the client while the real cause is logged server-side with a correlation ID the client also receives, so a support conversation can find the real error without ever exposing it.

## Threat model

| Threat                                                                              | Mitigation                                                                                                                                                                          | Verification                                                                                                                                                   |
| ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unauthorized admin access via a guessed/obscure URL                                 | Supabase Auth + live server-side role check on every admin Route Handler, not route-based obscurity                                                                                 | Live: unauthenticated `GET /admin` redirects; unauthenticated `POST /api/admin/*` returns `401`                                                                |
| IDOR on orders (guessing an order's internal UUID)                                  | The UUID alone resolves nothing to a student — tracking requires the `order_ref` **and** the secret token; admin routes require an authenticated admin session regardless of the ID | Live: `POST /api/track` with a right ref/wrong token returns a uniform `404`, never confirming which half was wrong                                            |
| Order-tracking enumeration                                                          | Token is the actual secret; rate-limited per-IP and per-`order_ref`, fail-closed                                                                                                    | Live: rate limit fires past threshold on both keys independently                                                                                               |
| Unrestricted Storage access to payment proofs                                       | Private bucket, zero RLS policies, access only via a Route-Handler-minted 5-minute signed URL after an authenticated admin role check                                               | Live: anon key gets an empty list and `404 Object not found`; a valid signed URL resolves the real file                                                        |
| Malicious file upload (polyglot, oversized, wrong type)                             | Magic-byte check + `sharp` re-encode + size limit, all server-side, shared between the student proof path and the admin QRIS path                                                   | Unit tests for each rejection path (`validate-image.test.ts`)                                                                                                  |
| Database write abuse (spamming reservations)                                        | Session- and IP-scoped rate limits (see table above)                                                                                                                                | Live: rate limit fires past threshold                                                                                                                          |
| Number reservation abuse / hoarding                                                 | One live reservation per session (structural), plus the Phase-14 per-IP reservation backstop against session-cycling                                                                | Live 20-way concurrency test (Phase 6): exactly one winner every time; A5 guard confirmed live                                                                 |
| Brute-force tracking token guessing                                                 | High-entropy CSPRNG token, rate-limited per `order_ref`                                                                                                                             | Rate-limit test                                                                                                                                                |
| Exposed secrets in source, history, or client bundle                                | No secret tracked in git; `.next` build output grepped clean for the local dev service-role key and DB password; no genuinely-in-use `NEXT_PUBLIC_*` value exists                   | `git grep`/build-output grep, this pass                                                                                                                        |
| PII leaks via logs                                                                  | Centralized redaction (`logger.ts`)                                                                                                                                                 | Live: real order submission, log grepped for name/email/phone/token — zero matches                                                                             |
| Overly broad RLS policies                                                           | There are none to be broad — every table has zero policies, changed only with an explicit, reviewed migration                                                                       | Live: anon key denied on every table and the private bucket                                                                                                    |
| Client-side privilege escalation (tampering with a disabled button, forged request) | Every client-side gate (`RoleGate`, `getAvailableActions`-derived row actions) has an independent, identical server-side check                                                      | Live: `ADMIN_KAMPUS` calling a `ADMIN_TELKOMSEL`-only endpoint directly (not through the UI) is refused with `403` the same as a hidden button would have been |
| Shared service-role client session poisoning                                        | Sign-in/refresh use a scoped, throwaway client; the shared singleton is never used for anything that mutates its own auth session                                                   | Live regression check: sequential logins by two different admins don't disturb later Storage calls (Phase 10-11 gate)                                          |

Each control above was verified live against the running application and the local Supabase stack during this session, not only reviewed by reading the code — see the per-phase gate reports in `docs/reports/` for the specific commands and results.
