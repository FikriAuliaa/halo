# Phase 15 Verification Gate (B119-B126: Testing)

## Built

- **B119** — `e2e/scenarios-a-e.spec.ts`: Scenario A (full happy-path order through the real browser UI), B (two genuinely independent Playwright contexts racing one number — exactly one 200, one 409, every time), C (reservation expiry via `RESERVATION_TTL_MINUTES_OVERRIDE`, gated behind that env var since it needs a real ~65s wait), D (a page reload mid-reservation leaves the same row, same `reserved_until`, untouched), E (submitting against a never-reserved number is refused, never partially accepted).
- **B120** — `e2e/scenarios-f-i.spec.ts`: F (a non-image file and a JPEG-header-plus-appended-script polyglot, both via direct API bypassing any client check — the polyglot is expected to _succeed_, since `reencodeImage`'s decode-then-re-encode is what discards the payload, not a rejection at the validation stage; a UI-level upload of a bad file is also asserted to surface a visible error), G (a real, valid JPEG upload reaches `pending`), H (admin verify moves the order to `verified` and the number to `sold`, atomically, with a matching `audit_log` row), I (admin reject moves the order to `rejected` and the number back to `available`, same atomicity/audit assertion).
- **B121** — `e2e/scenarios-j-l.spec.ts`: J (a `sold_offline` number returns `409 NUMBER_UNAVAILABLE` to a student), K (unauthenticated admin access denied both by page redirect and by two separate direct API calls — a read and a write), L (every real `ADMIN_TELKOMSEL`-only endpoint — `adminMarkSoldOffline`, `adminRunCleanup`, `adminForceReleaseReservation`, `adminConfirmPackagePrice`, `adminUpdatePaymentConfig` — refused with `403` for `ADMIN_KAMPUS`). `adminOverrideOrderStatus`, `adminUpdateSystemConfig`, and `adminManageAdmins` are declared in the permission matrix but have no implemented route in this build — an honest gap, not silently sampled around.
- **B122** — `e2e/a11y.spec.ts`: axe scans (serious/critical only) across three student and four admin screens, plus a real keyboard-only walk of number-select → reservation → package screen (Tab/Space/Enter, no mouse), asserting focus lands somewhere sensible (not `<body>`) after the client-side navigation.
- **B123** — `e2e/visual.spec.ts`: baseline screenshots at all six required widths (320-1440px) across three routes. No reference screenshots exist anywhere in this repository (confirmed by search in Phase 7-9) — this establishes baselines from the current implementation for _future_ regression detection, not a comparison against a supplied reference that was never provided. The home route's number grid is masked (it's a random sample re-shuffled every load, by design — an unmasked dynamic region exactly as B123 itself warns against). Baselines are `.gitignore`d, not committed: Playwright's snapshot filenames embed the OS, so macOS-generated baselines would falsely fail on the Linux CI runner; whoever runs this suite in CI establishes them there once.
- **B124** — `e2e/failure-modes.spec.ts`: a missing package reference, a missing university, and a malformed tracking request, each asserted to produce a clean 4xx (never a 500, never a partial write) against the real stack. The full matrix's remaining rows (Postgres/Storage unavailable, the cron job failing, a network interruption mid-upload, a server restart mid-reservation) would require actually taking down stack containers or injecting network faults — not built in this pass, and stubbing the repository instead would prove nothing about real behavior, which is the exact failure mode this block warns against. A fourth case, a deleted `system` config row, was verified **manually** rather than automated (see below) rather than risk a new class of parallelism collision.
- **B125** — `.github/workflows/ci.yml` (lint/typecheck/format → unit+integration with coverage → E2E+axe → production build, on every PR) and `.github/workflows/nightly.yml` (Scenario B repeated 25× plus the full E2E suite across both viewports, nightly). No standalone, dedicated concurrency test _suite_ exists yet — B066's formal version was explicitly deferred in the Phase 6 gate — so nightly's "repetition" is Scenario B repeated, a real but narrower substitute, documented as such in the workflow file itself rather than overstated.
- Also added: `tests/rls/policies.test.ts` — the `test:rls` npm script referenced a `tests/rls` directory that didn't exist (dead, from before the Supabase migration); this turns the manual anon-key-denial audit from Phase 14 into 11 standing regression assertions across every table and both Storage buckets.

## Two significant bugs found live during this phase, both fixed

1. **`personalDataFormSchema` — the `/data` screen could never be completed.** `data-form-screen.tsx` validated its four-field draft (`full_name`, `university`, `whatsapp`, `email`) against the _full_ `orderFormSchema`, which also requires `package_id` — a field this screen never collects (package selection happens on an earlier screen, tracked via `flow-state.ts`, and is only read back on the payment screen). Since `package_id` was always `undefined` in the draft, validation always failed, and `router.push("/bayar")` was never reached — silently, with no visible error, since the resulting error was attached to a field (`package_id`) this screen doesn't render. **No student could have completed an order through the real UI at all.** This was undetected through Phases 7-13 because verification there was API-route-only (`curl`), never an actual browser rendering the form and clicking through it — found the moment B119's Scenario A actually drove the real UI. Fixed by splitting a new `personalDataFormSchema` (the four collected fields) out of `orderFormSchema` (which now extends it with `package_id`), and pointing `data-form-screen.tsx` at the narrower one.
2. **Missing `ToastProvider` — every admin screen that shows a toast crashed with a 500.** `(admin)/admin/(dashboard)/layout.tsx` never wrapped its children in a `ToastProvider`, unlike the student layout. Any component calling `useToast()` unconditionally at render time — `AddNumberDialog`, `BulkAddDialog`, `NumberActions`, the order detail page's verify/reject buttons, `PackagesConfigClient`, `PaymentConfigClient` — threw `"useToast must be used within a ToastProvider"` the instant the page rendered, producing Next's generic error page instead of the real screen. This affected essentially every admin page built in Phases 11-13. Same root cause as bug 1: Phases 10-13's "live verification" tested API routes exclusively and never once loaded these pages in an actual browser. Found via `a11y.spec.ts`'s axe scan of `/admin/nomor` returning a `document-title`/`html-has-lang` violation — which turned out to be axe correctly describing Next's `__next_error__` boundary page, not the real screen. Fixed by wrapping the admin dashboard layout in `ToastProvider`; verified every admin page (`/admin`, `/admin/pesanan`, `/admin/pesanan/{id}`, `/admin/nomor`, all three `/admin/konfigurasi/*` screens) now returns `200` and renders the real content.

Both are recorded here plainly rather than folded quietly into the phase's "built" list, because they mean the Phase 10-13 gate reports' verification claims were narrower than they read — real, but backend-only. Noted for the Phase 17 code-quality review as well.

## A third, unrelated but severe bug found and fixed in the same pass

**The Phase 14 CSP broke all client-side JavaScript in dev mode.** `script-src 'self' 'nonce-...' 'strict-dynamic'` with no `unsafe-eval` blocked Next.js's dev-mode module evaluation entirely (`PAGEERROR: Evaluating a string as JavaScript violates the following Content Security Policy directive`) — every page loaded, but no client interactivity ever ran (no search, no reservation, nothing), silently. This was invisible to Phase 14's own verification because that pass checked response headers and static HTML only, never actually executed the page in a real JS engine — exactly the gap Playwright closes. Fixed by adding `'unsafe-eval'` to `script-src` only when `NODE_ENV !== "production"`; confirmed clean (no `unsafe-eval`, no console errors) against an actual `next build && next start` afterward.

## A test-infrastructure bug found and fixed (not an app bug)

Every spec file originally called a shared `cleanupTestData()` in its own `afterAll`, doing a wildcard `delete ... where number like '0899%'`. Under `fullyParallel`, Playwright's `afterAll` runs once **per worker**, not once globally — a fast-finishing file's worker could delete a `0899...` test number still actively in use by a slower test running concurrently in a different file, surfacing as "card not found" and `null` database rows with no consistent pattern. Fixed by removing the shared wildcard cleanup entirely; every test already owned deleting its own number in a `finally` block, which is both correct and sufficient. A second, related fix: repeated per-test admin logins across files collided with the intentionally tight admin-login rate limit (10/5min, B115) once the full suite ran together — fixed with `e2e/global-setup.ts`, logging in once per role for the whole run and sharing the saved `storageState` everywhere an authenticated session is needed.

## Deferred

- B066's formal, dedicated concurrency test suite (12 scenarios × repetition, deliberately-broken-guard verification) — still not built as a standalone artifact; the live 20-way test (Phase 6) and this phase's Scenario B (×1 and ×25) cover the single most important claim, not the full matrix.
- Most of B124's failure-mode matrix (infrastructure unavailability, network interruption, server restart) — genuinely requires fault injection this pass didn't build.
- CI/nightly workflows are written and locally sanity-checked (the exact commands they run were exercised manually against the local stack) but have not executed inside real GitHub Actions, since this environment has no way to do that.

## Verdict

The two bugs this phase found are the kind that only real browser-driven testing catches: a student could never have completed an order, and an admin could never have used most of the admin panel, despite every underlying API being correct and thoroughly verified. Both are fixed and now covered by the standing E2E suite so they can't silently return. Proceeding to Phase 16 (Operational Readiness).
